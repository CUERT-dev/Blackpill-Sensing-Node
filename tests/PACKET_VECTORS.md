# Team-generated GP protocol revision 10 UART packet vectors

These expected frames were calculated independently from the protocol specification (field layout, little-endian serialization, and CRC-16/CCITT-FALSE), rather than generated by `GP_EncodeUart`. They are team-generated regression vectors, not vectors supplied by Ali or an upstream protocol maintainer.

Each frame is 14 bytes. The CRC covers bytes 2 through 11 and is serialized little-endian.

## Vector 1: normal command

- Input: `sequence=0x1234`, `throttle_pm=500`, `steering_pm=-250`, `flags=0x05` (VALID | DEADMAN)
- Expected CRC: `0x3B19` (wire bytes `19 3B`)
- Expected bytes:

```text
A5 5A 02 01 07 34 12 F4 01 06 FF 05 19 3B
```

## Vector 2: maximum values

- Input: `sequence=0xFFFF`, `throttle_pm=1000`, `steering_pm=1000`, `flags=0x07` (VALID | ARM | DEADMAN)
- Expected CRC: `0x6C9F` (wire bytes `9F 6C`)
- Expected bytes:

```text
A5 5A 02 01 07 FF FF E8 03 E8 03 07 9F 6C
```

## Vector 3: invalid-stop command

- Input: `sequence=0x0001`, `throttle_pm=0`, `steering_pm=0`, `flags=0x00`
- Expected CRC: `0xABE9` (wire bytes `E9 AB`)
- Expected bytes:

```text
A5 5A 02 01 07 01 00 00 00 00 00 00 E9 AB
```

## Verification

`test_uart_sender.c` compares the complete output from the sender against these exact byte arrays. Keep the origin of these vectors documented. They provide useful independent regression coverage, but should not be described as Ali's upstream vectors.
